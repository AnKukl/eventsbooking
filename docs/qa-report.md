## 5. Функциональное тестирование (чёрный ящик)

80 из 89 сценариев прошли сразу. Из 9 расхождений 3 — ошибки моих ожиданий (событие уже было заполнено), остальные 6 —
реальные находки (раздел 6). Подтверждено:

- **Регистрация и вход:** дубль email (в том числе в другом регистре) → 409; невалидный email, короткий пароль, пароль
  73 байта, email 256 символов, пустое тело, битый JSON → 400; неверный `role` → 400; чужой content-type → 415; вход
  не различает «нет пользователя» и «неверный пароль»; хеш пароля в ответах нет.
- **Права:** аноним → 401; USER на создание, правку, удаление → 403; подделанный токен, мусор, `alg=none`, Basic → 401;
  `/actuator/info`, `/actuator/env` → 401.
- **Валидация событий:** пустое название, название 201 символ, дата в прошлом, дата без зоны, `capacity` 0 / −5 / строка /
  больше `int`, нет `organizerId` → 400. Юникод (кириллица, польские буквы, эмодзи) сохраняется корректно. HTML в названии
  хранится как текст. Дата со смещением `+02:00` принимается.
- **Пагинация:** `size=100000` ограничивается до 100; `size=0`, `page=-1`, `page=999999` → 200.
- **Бронирование:** бронь, дубль → 409, переполнение → 409 «Event is full», отмена >24 ч → 200, повторная отмена → 409,
  отмена <24 ч → 409, освободившееся место доступно другому, уменьшение `capacity` ниже занятых → 409, удаление события
  с бронями → 204 (каскад).
- **Конкурентность по HTTP:** 25 параллельных запросов на 3 места, 2 прогона: ровно **3 × 201 и 22 × 409**, 5xx нет,
  `bookedCount` = активные брони в БД = 3.
- **Kafka:** на каждую бронь ровно одно уведомление, дублей `event_id` нет.
- **Заголовки:** `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Cache-Control: no-store` присутствуют.

## 6. Найденные дефекты (по приоритету)

### Блокируют фронтенд
1. **CORS не настроен (новое).** Preflight `OPTIONS /api/events` с `Origin: http://localhost:5173` отвечает **401 без
   заголовков `Access-Control-*`**. Браузер заблокирует все запросы SPA с другого origin. Нужны `CorsConfigurationSource`
   в `SecurityConfig` (разрешённые origin из конфигурации, заголовки `Authorization`, `Content-Type`, методы GET/POST/PUT/
   DELETE, `OPTIONS` без токена) или прокси в dev-сервере фронтенда.
2. **IDOR при бронировании и отмене (P1, подтверждено).** Пользователь B отменил бронь пользователя A (200); `userId`
   берётся из тела, принимается любое число (в том числе `0` и отрицательное). Фронтенд не сможет честно показывать
   «мои брони», пока пользователь не берётся из токена.
3. **Любой может стать ORGANIZER (P1, подтверждено)** и **любой организатор правит чужое событие (P1, подтверждено:
   `PUT` → 200).** Фронтенду нужны разные интерфейсы для ролей, а они сейчас ничем не защищены.

### Заметные
4. **`GET /api/events?sort=foo` → 500** (в логе стектрейс); `sort=version` → 200 (внутреннее поле). Фронтенд с
   сортировкой по колонкам упадёт на опечатке.
5. **При падении PostgreSQL:** `/actuator/health` не отвечает 20+ с, вход и любой запрос висят ≈ 32 с и дают **500**
   вместо 503 (ждут `connection-timeout` Hikari, 30 с). Потоки забиваются, фронтенд увидит «вечную загрузку».
   Нужны: `spring.datasource.hikari.connection-timeout` 2–3 с, обработчик `CannotCreateTransactionException` /
   `DataAccessResourceFailureException` → 503 `ProblemDetail`.
6. **При падении Kafka** каждая бронь тормозит ровно на 2 с (`max.block.ms`), событие теряется (так и задумано, описано в
   decisions 006), `/actuator/health` остаётся UP (Kafka не входит в health). После возврата Kafka producer и consumer
   восстановились сами. Желательно: отправка в отдельном потоке/outbox, чтобы бронь не ждала.
7. **Бронь начавшегося события и несуществующего пользователя разрешена**; нет `@Positive` на `userId`.
8. **Конфликт версий события при `PUT`/`DELETE` → 500** (по коду, см. docs/review.md п. 5).

### Мелочи
9. `restart: no` у сервиса `app` в compose: после падения процесса контейнер не поднимется сам (нужен
   `restart: unless-stopped`).
10. `capacity` без верхней границы (создано событие на 2 147 483 647 мест).
11. `@Future` в `PUT` не даёт исправить название уже начавшегося события.
12. При удалении события уведомления остаются без брони (в `notifications` нет внешнего ключа; допустимо как история).
13. Swagger и `/v3/api-docs` открыты в продакшене (springdoc предупреждает в логе).
14. Нет эндпоинтов, которые понадобятся фронтенду: `GET /api/me`, «мои брони», список броней события, выход/refresh
    токена (токен живёт 1 час без продления).
15. Предупреждения в тестах про диалект Hibernate (п. 3).

## 7. Что нужно для фронтенда (резюме)

1. CORS (п. 1), без него фронтенд в браузере не заработает.
2. Пользователь из токена + владение (п. 2, 3): `GET /api/me`, `POST /api/events/{id}/bookings` без `userId`,
   `GET /api/bookings/my`, закрытая роль ORGANIZER.
3. Корректные 4xx вместо 500 (п. 4, 8) и 503 при недоступной БД (п. 5).
4. Контракт: OpenAPI уже есть, по нему можно генерировать типы клиента.
