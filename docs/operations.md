# Эксплуатация

## Фоновые задачи очистки

Обе задачи запускаются по cron (время сервера) и выполняются на одном инстансе: блокировка ShedLock в таблице
`shedlock`. Инстанс, которому блокировка не досталась, пропускает запуск и пишет об этом в лог. Если инстанс упал с
блокировкой, она освобождается через 30 минут. В тестах расписание выключено (`app.scheduling.enabled=false`).

| Задача | Когда | Что делает |
|---|---|---|
| `IdempotencyKeyCleanupJob` | `app.cleanup.idempotency.cron`, по умолчанию `0 0 3 * * *` (03:00) | удаляет ключи `Idempotency-Key`, у которых прошёл `expires_at` |
| `OrphanFileCleanupJob` | `app.cleanup.orphans.cron`, по умолчанию `0 30 3 * * *` (03:30) | удаляет брошенные загрузки и файлы без строки в `event_images` |

### Ключи идемпотентности

- Срок жизни ключа задаёт `app.idempotency.ttl` (по умолчанию `PT24H`). `expires_at` выставляется при создании ключа.
- Удаление идёт пачками (`app.cleanup.idempotency.batch-size`, 1000): `DELETE ... WHERE id IN (SELECT ... LIMIT n)`,
  пока очередная пачка не удалит ноль строк. Между пачками пауза `app.cleanup.idempotency.pause` (`PT0.1S`).
- Итог прогона пишется в лог INFO: `Idempotency cleanup finished: removed N expired keys in M batches`.

### Брошенные файлы (сироты)

Каждый загруженный файл имеет строку в `event_images`: `PENDING` с момента загрузки, `ATTACHED` после прикрепления к
событию. Задача делает три прохода:

1. **База:** строки `PENDING` старше grace-периода удаляются вместе с файлом. Сначала удаляется строка (только если она
   всё ещё `PENDING`), потом файл, поэтому загрузка, прикреплённая в эту же секунду, не пострадает.
2. **Файлы:** каталог хранилища обходится потоком (`Files.walk`). Файл старше grace-периода (по времени изменения), у
   которого нет строки, удаляется. Ключи сверяются с базой пачками по `app.cleanup.orphans.batch-size` (500). Символические
   ссылки пропускаются, а любой путь, нормализованный за пределы каталога, игнорируется.
3. **Отчёт:** строки `ATTACHED` без файла только пишутся в лог WARN. Удалять их задача не будет: на них ссылается событие.

Настройки: `app.cleanup.orphans.grace` (по умолчанию `PT24H`), `app.cleanup.orphans.dry-run` (по умолчанию `true`),
каталог — `app.storage.local-dir` (переменная `STORAGE_DIR`, в Docker — том `uploads`).

**Как включить удаление сирот.** По умолчанию задача работает в режиме dry run: только считает и пишет итог в лог INFO
(`Orphan cleanup finished (dry run, nothing removed): ...`). Порядок включения:

1. Дать задаче поработать несколько ночей и посмотреть числа в логе. Если «files without a row» неожиданно велико, сначала
   разобраться (например, в каталог попали чужие файлы), и только потом включать удаление.
2. Включить удаление: `CLEANUP_ORPHANS_DRY_RUN=false` (в Docker Compose переменная уже проброшена) и перезапустить
   приложение.

```
# PowerShell
$env:CLEANUP_ORPHANS_DRY_RUN = "false"
docker compose up -d
```

### Метрики

| Счётчик Micrometer | Что считает |
|---|---|
| `cleanup.idempotency.keys.deleted` | удалённые просроченные ключи идемпотентности |
| `cleanup.orphans.pending.deleted` | удалённые строки `PENDING` старше grace-периода (вместе с файлами) |
| `cleanup.orphans.files.deleted` | удалённые файлы без строки |
| `cleanup.orphans.attached.missing` | найденные строки `ATTACHED` без файла (только отчёт) |

В режиме dry run счётчики удалений не растут, найденное видно только в логе. Эндпоинт `/actuator/metrics` по умолчанию не
открыт (`management.endpoints.web.exposure.include=health,info`). Чтобы смотреть счётчики, добавьте `metrics` в этот список.
Эндпоинт будет требовать токен, как и всё, что не открыто явно.
