# Архитектурные решения

Короткие записи о решениях, которые нельзя восстановить по коду. Новые — добавлять сверху.

## 009. Избранное: идемпотентность на уровне БД, открытый для гостей каталог

**Статус:** принято.

- **Таблица `favorites` (V7).** `UNIQUE (user_id, event_id)` — единственный арбитр дубля; индекс
  `(user_id, created_at DESC)` обслуживает «мои избранные, новые сверху». `event_id` с `ON DELETE CASCADE`: удалённое
  событие уходит из избранного. FK на `users` нет, как у `bookings.user_id` (см. 002): токен со старым `sub` после
  очистки БД иначе давал бы 500 вместо работающего API.
- **POST идемпотентен без гонок.** Один `INSERT ... SELECT ... ON CONFLICT DO NOTHING`: 1 строка — создано (201),
  0 — уже было (200) либо события нет; тогда `existsById` отличает 404. Проверки «есть ли запись» перед вставкой нет,
  поэтому два параллельных POST не создадут дубль и не вернут 500. Время записи берётся из `Clock`.
- **DELETE** всегда 204 (в том числе для чужого или несуществующего события): повтор безопасен, наличие чужих записей
  не раскрывается.
- **`isFavorite` без N+1.** Для страницы событий один запрос `... WHERE event_id IN (...)`. Гость (нет токена) — `false`
  без обращения к БД.
- **Каталог открыт для гостей.** `GET /api/events` и `/api/events/{id}` теперь без токена (раньше требовали его): иначе
  «для гостя `isFavorite=false`» недостижимо и неавторизованный посетитель фронтенда не увидит даже список. Изменение
  мероприятий и всё остальное по-прежнему только с токеном (deny by default). Неверный токен даже на открытом
  эндпоинте даёт 401.
- **`seatStatus`.** `AVAILABLE` / `SOLD_OUT` вычисляются из `bookedCount` и `capacity`. `WAITLIST` есть в контракте,
  но не выдаётся: листа ожидания нет, полное событие — `SOLD_OUT`. Появится вместе с самой функцией.
- **Порядок избранного фиксирован** (последнее добавленное первым), параметр `sort` даёт 400.

## 008. Личность из токена, владение данными и закрытая роль ORGANIZER

**Статус:** принято. Закрывает пункты 1–3 «известных упрощений» из 005 и P1 из docs/review.md.

**Проблема.** `userId` брони и `organizerId` события приходили в теле запроса, отмену мог выполнить кто угодно, а роль
`ORGANIZER` выбиралась при регистрации. Любой аутентифицированный пользователь мог действовать от имени другого.

**Решение.**
- Пользователь — это `sub` проверенного JWT (`CurrentUser.id(principal)`); клиент его не передаёт. `POST .../bookings`
  больше не принимает тело, `organizerId` убран из `EventRequest` (лишние поля в теле игнорируются).
- Событие может менять и удалять только создавший его организатор (`403`). Владелец при `PUT` не меняется.
- Чужую бронь нельзя отменить: ответ `404`, как для несуществующей, чтобы не раскрывать, какие брони есть.
- Роль не выбирается клиентом. `ORGANIZER` создаётся только при верном `inviteCode`, который задаётся переменной
  `ORGANIZER_INVITE_CODE` (секрет, по умолчанию пустой, то есть организаторов регистрировать нельзя). Сравнение
  выполняется за постоянное время (`MessageDigest.isEqual`) и раньше проверки занятости email, чтобы неверный код не
  использовался для перебора адресов.
- Новые эндпоинты для интерфейса: `GET /api/me` (кто я), `GET /api/bookings/my` (мои брони, новые сверху).
- Бронь события, которое уже началось, запрещена (`409 Event already started`).
- Сортировка списков только по белому списку полей (`400` вместо `500` и без доступа к внутренним полям).
- `OptimisticLockingFailureException` отдаётся как `409`, недоступная БД — как `503` с `Retry-After`; пул соединений
  ждёт 3 с вместо 30.
- CORS: разрешены только origin из `app.cors.allowed-origins` (`CORS_ALLOWED_ORIGINS`, по умолчанию
  `localhost:5173` и `localhost:3000`), без cookie. Preflight проходит без токена, а ответы 401/403 тоже содержат
  CORS-заголовки, иначе браузерный клиент не увидит причину ошибки.

**Компромиссы.** Это ломает контракт API (тело брони, `organizerId`, поле `role`); клиентов пока нет, поэтому цена мала.
Организатор по-прежнему не может передать событие другому и нет роли администратора; код приглашения общий, а не
персональный. Токен по-прежнему нельзя отозвать до `exp`. Организатор не может отменить чужую бронь на своё событие.

## 007. Поставка: Docker, GitHub Actions, OpenAPI

**Статус:** принято.

**Решение и причины.**
- **Многоэтапный Dockerfile** (JDK для сборки, JRE для запуска, слои Spring Boot, пользователь без прав). В образе нет
  Maven, исходников и компилятора: он меньше и атакуемая поверхность меньше. Слои зависимостей кэшируются, поэтому
  правка кода не перекачивает библиотеки. Тесты в сборку образа не входят: им нужен Docker (Testcontainers), их гоняет CI.
- **Секреты только через окружение.** `JWT_SECRET` и пароль БД не пишутся ни в Dockerfile, ни в образ; `.dockerignore`
  исключает `.env`, ключи и `.git`. В compose у `JWT_SECRET` нет значения по умолчанию (`${JWT_SECRET:?...}`): лучше
  отказ на старте, чем контейнер с известным всем секретом. Проверено поиском значения секрета в слоях образа.
- **Два адреса Kafka** в compose: `localhost:9092` для приложения на хосте и `kafka:19092` для контейнеров; иначе брокер
  отдаёт клиенту адрес, недоступный из его сети. Приложение стартует только после healthy у PostgreSQL и Kafka.
- **CI** (`.github/workflows/ci.yml`): `./mvnw verify` на каждый push и pull request, Java 25 (Temurin), кэш Maven.
  Интеграционные тесты идут на реальных PostgreSQL и Kafka из Testcontainers (Docker есть на `ubuntu-latest`), а не на
  H2 и моках: ошибки миграций, индексов и гонок видны до слияния.
- **OpenAPI** (springdoc) и Swagger UI открыты без токена, потому что описывают контракт, а не данные; все `/api/**`
  остаются закрытыми. Схема безопасности `bearerAuth` (JWT) позволяет пробовать защищённые методы кнопкой Authorize.

**Компромиссы.** Документация открыта и в продакшене: для публичного API это норма, для внутреннего её стоит закрыть
или отключить (`springdoc.api-docs.enabled=false`). Образ не сканируется на уязвимости, версии базовых образов не
закреплены по digest, а нетестовая сборка в образе не проверяет, что тесты зелёные, — это делает только CI.

## 006. Kafka: BookingCreated публикуется после коммита, consumer идемпотентен

**Статус:** принято.

**Решение.**
- После успешной брони `BookingService` публикует `BookingCreated` в топик `booking-events` (`KafkaTemplate`, JSON,
  ключ = `bookingId`). Публикация идёт **после коммита**, а не внутри транзакции: `inTransactionWithRetry` уже вернулся,
  то есть транзакция зафиксирована. Так потребители не узнают о брони, которую откатили (например, при конфликте версий
  и повторе). Сообщение содержит `eventId` (UUID) — ключ идемпотентности.
- Ошибка публикации логируется и не ломает бронь: она уже зафиксирована, отвечать клиенту ошибкой было бы ложью.
  `max.block.ms=2s`, иначе при недоступном Kafka каждая бронь ждала бы 60 с (так и было, пока не нашли тестами).
- Consumer (`BookingEventsListener`, группа `notifications`) пишет строку в `notifications` через
  `INSERT ... ON CONFLICT (event_id) DO NOTHING`. Уникальность `event_id` решает БД атомарно, поэтому повторная
  доставка и гонка двух consumer не создают дубль. Проверка «сначала SELECT» была бы небезопасна при гонке.

**Что будет при падении consumer.**
- *Consumer остановлен:* сообщения копятся в Kafka (хранение по умолчанию 7 дней), бронирования продолжают работать.
  После запуска consumer продолжает с сохранённого offset группы и догоняет; уведомления приходят с задержкой.
- *Упал посреди обработки:* offset фиксируется только после успешной обработки, значит сообщение придёт снова
  (at-least-once). Дубль безопасен благодаря идемпотентности выше.
- *Временная ошибка (например, БД недоступна):* `DefaultErrorHandler` повторяет 3 раза с паузой 1 с.
- *Повторы исчерпаны или сообщение нечитаемо:* запись логируется и **пропускается**, чтобы одна плохая запись не
  блокировала партицию; нечитаемые сообщения не повторяются вовсе. Уведомление при этом **теряется**. Следующий шаг —
  dead letter topic (см. README).
- *Падение приложения между коммитом брони и отправкой в Kafka:* событие **теряется** (dual write). Брони и
  уведомления разойдутся.

**Известные упрощения.**
1. Нет dead letter topic (`booking-events.DLT`) и повторной обработки; нет алертов на пропущенные записи.
2. Нет transactional outbox: надёжная схема — писать событие в таблицу `outbox` в той же транзакции, что и бронь, а
   отдельный процесс публикует его в Kafka. Тогда событие не теряется при падении между коммитом и send.
3. Отмена брони событие не публикует (в задаче только `BookingCreated`).
4. Топик создаётся приложением (3 партиции, 1 реплика) — для разработки; в продакшене топиками управляет инфраструктура.

## 005. Аутентификация: Spring Security 7, stateless, JWT (HS256)

**Статус:** принято.

**Решение.**
- `SecurityFilterChain`: без сессий (`STATELESS`), CSRF отключён осознанно — токен передаётся явно в заголовке
  `Authorization`, куки не используются, браузер не может подставить его сам. Всё, что не перечислено в правилах,
  требует аутентификации (deny by default).
- Открыто: `POST /api/auth/register`, `POST /api/auth/login`, `/actuator/health`. Только `ORGANIZER`:
  `POST /api/events`, `PUT|DELETE /api/events/{id}`. Остальное — любой аутентифицированный пользователь.
- JWT выдаёт `JwtService` (Nimbus, HS256), проверяет на каждом запросе стандартный фильтр resource-server;
  собственного фильтра нет. Claims: `sub` = id пользователя, `iss`, `iat`, `exp`, `roles` (["ORGANIZER"]).
  Проверяются подпись, срок (по бину `Clock`, без допуска на рассинхронизацию) и издатель.
- Секрет — только из переменной окружения `JWT_SECRET`, значения по умолчанию нет, минимум 32 байта;
  иначе приложение не стартует. `toString()` у `JwtProperties`, `IssuedToken`, запросов с паролем скрывает секреты.
- Пароли — `BCryptPasswordEncoder` (хеш вида `$2a$10$…`); пароль в байтах UTF-8 не длиннее 72 (ограничение BCrypt).
- 401 и 403 из фильтров передаются в MVC-резолверы и отдаются как `ProblemDetail` тем же `ApiExceptionHandler`
  (401 содержит `WWW-Authenticate: Bearer`). Токены и пароли не логируются (проверяется тестом по захваченному выводу).
- Логин не раскрывает, существует ли email: одинаковый ответ и выравнивание времени проверкой по «пустому» хешу.
  Регистрация, наоборот, отвечает `409` на занятый email — это стандартный компромисс удобства и приватности.

**Известные упрощения и открытые вопросы (важно!).** Пункты 1–3 закрыты решением 008.
1. **Любой может зарегистрироваться как `ORGANIZER`** (поле `role` в запросе). Иначе в системе негде взять
   организатора без администратора. Для продакшена: убрать поле, добавить роль ADMIN или подтверждение организаторов.
2. **Брони не привязаны к токену.** `POST /api/events/{id}/bookings` по-прежнему принимает `userId` в теле, а отмена
   не проверяет владельца: аутентифицированный пользователь может бронировать и отменять за другого. Следующий шаг —
   брать пользователя из `sub` токена и разрешать отмену только владельцу.
3. **`organizerId` в событии не привязан к токену**: любой `ORGANIZER` может создать/изменить событие от имени
   другого и менять чужие события. Следующий шаг — владелец события = автор из токена.
4. Нет refresh-токенов и отзыва токена: токен действует до `exp` (по умолчанию 1 час).
5. Нет ограничения частоты попыток логина (brute force); нужен rate limiting на уровне шлюза или фильтра.
6. Пакеты `security` и `user` зависят друг от друга (`JwtService` знает `User`/`Role`); при росте — вынести
   интерфейс выдачи токена.

## 004. Отмена брони: мягкая отмена, правило N часов через `Clock`

**Статус:** принято. Уточняет 001 (уникальность).

**Правило.** Отмена запрещена, если до начала события осталось *меньше* `app.booking.cancellation-notice`
(по умолчанию `24h`). Ровно 24 часа — ещё можно, 23 ч 59 мин — уже нельзя. Начавшееся событие отменить нельзя.
Нарушение — `409 Conflict` (`Cancellation not allowed`, ProblemDetail).

**Решение.**
- Время берётся только из бина `Clock` (`ClockConfig`, `Clock.systemUTC()`). Тесты подставляют
  `Clock.fixed(...)`, поэтому в них нет `Thread.sleep` и реального `now()`.
- Срок задаётся `BookingProperties` (`app.booking.cancellation-notice`), а не константой в коде.
- Отмена — *мягкая*: бронь остаётся в БД со статусом `CANCELLED` и `cancelled_at`; история сохраняется.
- Место возвращается через `Event.release()` (`bookedCount--`) в той же транзакции. Это меняет версию
  события, поэтому отмена защищена той же оптимистической блокировкой и повтором, что и бронирование
  (две параллельные отмены одной брони возвращают место только один раз, вторая получает
  `409 Already cancelled`).
- Повторная отмена — `409`, а не молчаливый успех: явная ошибка проще для клиента и исключает
  двойной возврат места.
- Эндпоинт: `POST /api/events/{eventId}/bookings/{bookingId}/cancel` (меняет состояние, а не удаляет ресурс).

**Изменение уникальности.** Полное ограничение `UNIQUE (event_id, user_id)` из 001 заменено на частичный
уникальный индекс `uq_bookings_active_event_user ... WHERE status = 'ACTIVE'`. Иначе отменивший бронь
пользователь никогда не смог бы забронировать то же событие снова. Гарантия «один пользователь —
одна *активная* бронь» сохраняется на уровне БД.

**Открытые вопросы.**
- Кто имеет право отменять бронь, не проверяется: в проекте пока нет аутентификации. Когда она появится,
  отменять сможет только владелец брони (и, возможно, организатор).
- Часовой пояс не важен: сравниваются моменты времени (`Instant`).

## 001. Бронирование: оптимистическая блокировка через `@Version`

**Статус:** принято.

**Задача.** Нельзя превысить `capacity` события и нельзя дважды забронировать одно событие одним
пользователем, в том числе при одновременных запросах.

**Решение.**
- В `Event` добавлено поле `@Version version` и счётчик `bookedCount`. Бронь вызывает `Event.book()`,
  который увеличивает счётчик (и этим меняет версию) либо бросает `EventFullException`.
- Бронь — запись в `bookings (event_id, user_id)`. Каждая попытка выполняется в своей транзакции
  (`TransactionTemplate` в `BookingService`): прочитать событие → проверить дубль → `book()` →
  `saveAndFlush(booking)`.
- Две транзакции, прочитавшие одно и то же «осталось одно место», обе пытаются выполнить
  `UPDATE events ... WHERE id = ? AND version = ?`. Выигрывает первая; вторая получает
  `OptimisticLockingFailureException`.
- Проигравшая транзакция **повторяется** (до `BookingService.MAX_ATTEMPTS = 5`) в новой транзакции:
  если место осталось — займёт его, если нет — получит `EventFullException`. Если повторы
  исчерпаны, клиент получает `ConcurrentBookingException` (тоже 409, можно повторить запрос).

**Защита на уровне БД (последняя линия обороны, не заменяет логику выше):**
- `UNIQUE (event_id, user_id)` — один пользователь не может забронировать событие дважды, даже
  если две транзакции обошли проверку `existsBy...`. Нарушение превращается в `AlreadyBookedException`.
- `CHECK (booked_count >= 0 AND booked_count <= capacity)` — БД не даст записать переполнение,
  даже если ошибка в коде обойдёт `Event.book()`.

**Ошибки клиенту.** Все бизнес-конфликты наследуют `ConflictException` и отдаются как
`409 Conflict` в формате `ProblemDetail` через `ApiExceptionHandler`:
`Event is full`, `Already booked`, `Concurrent booking conflict`, `Capacity below bookings`.

**Почему оптимистическая, а не пессимистическая блокировка.**
- Транзакция короткая, а конфликт возникает только когда несколько человек одновременно берут места
  *одного и того же* события. Для типичного события это редкость, поэтому дешевле обнаружить
  конфликт при записи, чем заставлять каждый запрос ждать блокировку строки (`SELECT ... FOR UPDATE`).
- Нет блокировок БД, которые держатся между чтением и записью, нет риска взаимоблокировок.
- Проигравший просто повторяется и получает корректный результат.

**Компромиссы и когда пересмотреть.**
- При очень высокой конкуренции за одно событие (мгновенная распродажа) повторов становится много,
  а у части запросов исчерпываются попытки (ответ 409 «повторите»). Для такого сценария лучше
  атомарный `UPDATE events SET booked_count = booked_count + 1 WHERE id = ? AND booked_count < capacity`
  или пессимистическая блокировка.
- `booked_count` — денормализованный счётчик. Он должен меняться вместе с `bookings`; сейчас это
  делает только `BookingService`. Когда появится отмена брони, она обязана уменьшать счётчик в той
  же транзакции.
- Изменение `capacity` ниже уже занятых мест отклоняется (`409 Capacity below bookings`).

**Проверка.** `BookingConcurrencyIntegrationTest` (Testcontainers, настоящий PostgreSQL):
два параллельных бронирования последнего места — одно успешно, второе `EventFullException`;
12 параллельных бронирований на 3 места — успешных не больше 3, счётчик совпадает с числом броней;
устаревшая версия сущности отклоняется; уникальное ограничение и `CHECK` работают в БД.

## 002. Связи таблиц: каскадное удаление событий и отсутствие FK на users

**Статус:** принято частично; FK на `users` отложен.

- **Каскад.** `bookings.event_id` ссылается на `events(id)` с `ON DELETE CASCADE`: бронь не имеет смысла без
  события. Если понадобится запретить удаление события с бронями, заменить на `RESTRICT` и обработать ошибку.
  Уведомления (`notifications`) при этом остаются как история: у них нет внешнего ключа на брони.
- **Нет FK на `users`.** `bookings.user_id` и `events.organizer_id` не имеют внешнего ключа. Когда это решалось,
  пользователей в системе не было. Сейчас они есть, и пользователь берётся из проверенного токена (решение 008),
  поэтому «несуществующий пользователь» практически невозможен через API, но на уровне БД это не гарантировано.
  Следующий шаг: миграция с внешними ключами (V8; V7 занята избранным) (с `ON DELETE RESTRICT`: учётную запись с бронями и событиями
  удалять нельзя) и тест на неё.
