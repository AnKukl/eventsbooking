# Архитектурные решения

Короткие записи о решениях, которые нельзя восстановить по коду. Новые — добавлять сверху.

## 005. Аутентификация: Spring Security 7, stateless, JWT (HS256)

**Статус:** принято.

**Решение.**
- `SecurityFilterChain`: без сессий (`STATELESS`), CSRF отключён осознанно — токен передаётся явно в заголовке
  `Authorization`, куки не используются, браузер не может подставить его сам. Всё, что не перечислено в правилах,
  требует аутентификации (deny by default).
- Открыто: `POST /api/auth/register`, `POST /api/auth/login`, `/actuator/health`. Только `ORGANIZER`:
  `POST /api/events`, `PUT|DELETE /api/events/{id}`. Остальное — любой аутентифицированный пользователь.
- JWT выдаёт `JwtService` (Nimbus, HS256), проверяет на каждом запросе стандартный фильтр resource-server;
  собственного фильтра нет. Claims: `sub` = id пользователя, `iss`, `iat`, `exp`, `roles` (["ORGANIZER"]).
  Проверяются подпись, срок (по бину `Clock`, без допуска на рассинхронизацию) и издатель.
- Секрет — только из переменной окружения `JWT_SECRET`, значения по умолчанию нет, минимум 32 байта;
  иначе приложение не стартует. `toString()` у `JwtProperties`, `IssuedToken`, запросов с паролем скрывает секреты.
- Пароли — `BCryptPasswordEncoder` (хеш вида `$2a$10$…`); пароль в байтах UTF-8 не длиннее 72 (ограничение BCrypt).
- 401 и 403 из фильтров передаются в MVC-резолверы и отдаются как `ProblemDetail` тем же `ApiExceptionHandler`
  (401 содержит `WWW-Authenticate: Bearer`). Токены и пароли не логируются (проверяется тестом по захваченному выводу).
- Логин не раскрывает, существует ли email: одинаковый ответ и выравнивание времени проверкой по «пустому» хешу.
  Регистрация, наоборот, отвечает `409` на занятый email — это стандартный компромисс удобства и приватности.

**Известные упрощения и открытые вопросы (важно!).**
1. **Любой может зарегистрироваться как `ORGANIZER`** (поле `role` в запросе). Иначе в системе негде взять
   организатора без администратора. Для продакшена: убрать поле, добавить роль ADMIN или подтверждение организаторов.
2. **Брони не привязаны к токену.** `POST /api/events/{id}/bookings` по-прежнему принимает `userId` в теле, а отмена
   не проверяет владельца: аутентифицированный пользователь может бронировать и отменять за другого. Следующий шаг —
   брать пользователя из `sub` токена и разрешать отмену только владельцу.
3. **`organizerId` в событии не привязан к токену**: любой `ORGANIZER` может создать/изменить событие от имени
   другого и менять чужие события. Следующий шаг — владелец события = автор из токена.
4. Нет refresh-токенов и отзыва токена: токен действует до `exp` (по умолчанию 1 час).
5. Нет ограничения частоты попыток логина (brute force); нужен rate limiting на уровне шлюза или фильтра.
6. Пакеты `security` и `user` зависят друг от друга (`JwtService` знает `User`/`Role`); при росте — вынести
   интерфейс выдачи токена.

## 004. Отмена брони: мягкая отмена, правило N часов через `Clock`

**Статус:** принято. Уточняет 001 (уникальность).

**Правило.** Отмена запрещена, если до начала события осталось *меньше* `app.booking.cancellation-notice`
(по умолчанию `24h`). Ровно 24 часа — ещё можно, 23 ч 59 мин — уже нельзя. Начавшееся событие отменить нельзя.
Нарушение — `409 Conflict` (`Cancellation not allowed`, ProblemDetail).

**Решение.**
- Время берётся только из бина `Clock` (`ClockConfig`, `Clock.systemUTC()`). Тесты подставляют
  `Clock.fixed(...)`, поэтому в них нет `Thread.sleep` и реального `now()`.
- Срок задаётся `BookingProperties` (`app.booking.cancellation-notice`), а не константой в коде.
- Отмена — *мягкая*: бронь остаётся в БД со статусом `CANCELLED` и `cancelled_at`; история сохраняется.
- Место возвращается через `Event.release()` (`bookedCount--`) в той же транзакции. Это меняет версию
  события, поэтому отмена защищена той же оптимистической блокировкой и повтором, что и бронирование
  (две параллельные отмены одной брони возвращают место только один раз, вторая получает
  `409 Already cancelled`).
- Повторная отмена — `409`, а не молчаливый успех: явная ошибка проще для клиента и исключает
  двойной возврат места.
- Эндпоинт: `POST /api/events/{eventId}/bookings/{bookingId}/cancel` (меняет состояние, а не удаляет ресурс).

**Изменение уникальности.** Полное ограничение `UNIQUE (event_id, user_id)` из 001 заменено на частичный
уникальный индекс `uq_bookings_active_event_user ... WHERE status = 'ACTIVE'`. Иначе отменивший бронь
пользователь никогда не смог бы забронировать то же событие снова. Гарантия «один пользователь —
одна *активная* бронь» сохраняется на уровне БД.

**Открытые вопросы.**
- Кто имеет право отменять бронь, не проверяется: в проекте пока нет аутентификации. Когда она появится,
  отменять сможет только владелец брони (и, возможно, организатор).
- Часовой пояс не важен: сравниваются моменты времени (`Instant`).

## 001. Бронирование: оптимистическая блокировка через `@Version`

**Статус:** принято.

**Задача.** Нельзя превысить `capacity` события и нельзя дважды забронировать одно событие одним
пользователем, в том числе при одновременных запросах.

**Решение.**
- В `Event` добавлено поле `@Version version` и счётчик `bookedCount`. Бронь вызывает `Event.book()`,
  который увеличивает счётчик (и этим меняет версию) либо бросает `EventFullException`.
- Бронь — запись в `bookings (event_id, user_id)`. Каждая попытка выполняется в своей транзакции
  (`TransactionTemplate` в `BookingService`): прочитать событие → проверить дубль → `book()` →
  `saveAndFlush(booking)`.
- Две транзакции, прочитавшие одно и то же «осталось одно место», обе пытаются выполнить
  `UPDATE events ... WHERE id = ? AND version = ?`. Выигрывает первая; вторая получает
  `OptimisticLockingFailureException`.
- Проигравшая транзакция **повторяется** (до `BookingService.MAX_ATTEMPTS = 5`) в новой транзакции:
  если место осталось — займёт его, если нет — получит `EventFullException`. Если повторы
  исчерпаны, клиент получает `ConcurrentBookingException` (тоже 409, можно повторить запрос).

**Защита на уровне БД (последняя линия обороны, не заменяет логику выше):**
- `UNIQUE (event_id, user_id)` — один пользователь не может забронировать событие дважды, даже
  если две транзакции обошли проверку `existsBy...`. Нарушение превращается в `AlreadyBookedException`.
- `CHECK (booked_count >= 0 AND booked_count <= capacity)` — БД не даст записать переполнение,
  даже если ошибка в коде обойдёт `Event.book()`.

**Ошибки клиенту.** Все бизнес-конфликты наследуют `ConflictException` и отдаются как
`409 Conflict` в формате `ProblemDetail` через `ApiExceptionHandler`:
`Event is full`, `Already booked`, `Concurrent booking conflict`, `Capacity below bookings`.

**Почему оптимистическая, а не пессимистическая блокировка.**
- Транзакция короткая, а конфликт возникает только когда несколько человек одновременно берут места
  *одного и того же* события. Для типичного события это редкость, поэтому дешевле обнаружить
  конфликт при записи, чем заставлять каждый запрос ждать блокировку строки (`SELECT ... FOR UPDATE`).
- Нет блокировок БД, которые держатся между чтением и записью, нет риска взаимоблокировок.
- Проигравший просто повторяется и получает корректный результат.

**Компромиссы и когда пересмотреть.**
- При очень высокой конкуренции за одно событие (мгновенная распродажа) повторов становится много,
  а у части запросов исчерпываются попытки (ответ 409 «повторите»). Для такого сценария лучше
  атомарный `UPDATE events SET booked_count = booked_count + 1 WHERE id = ? AND booked_count < capacity`
  или пессимистическая блокировка.
- `booked_count` — денормализованный счётчик. Он должен меняться вместе с `bookings`; сейчас это
  делает только `BookingService`. Когда появится отмена брони, она обязана уменьшать счётчик в той
  же транзакции.
- Изменение `capacity` ниже уже занятых мест отклоняется (`409 Capacity below bookings`).

**Проверка.** `BookingConcurrencyIntegrationTest` (Testcontainers, настоящий PostgreSQL):
два параллельных бронирования последнего места — одно успешно, второе `EventFullException`;
12 параллельных бронирований на 3 места — успешных не больше 3, счётчик совпадает с числом броней;
устаревшая версия сущности отклоняется; уникальное ограничение и `CHECK` работают в БД.

## 002. `bookings.user_id` и `events.organizer_id` без внешнего ключа на `users`

**Статус:** временно.

В проекте пока нет API создания пользователей, поэтому внешний ключ заставил бы заводить
пользователей вручную в каждом тесте. Когда появится управление пользователями, добавить FK отдельной
миграцией.

## 003. Удаление события удаляет его брони

`bookings.event_id` ссылается на `events(id)` с `ON DELETE CASCADE`: бронь не имеет смысла без события.
Если понадобится запретить удаление события с бронями, заменить на `RESTRICT` и обработать ошибку.
