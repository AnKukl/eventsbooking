## P1

### 1. Бронь и отмена не привязаны к токену (IDOR)
- **Где:** `BookingController.book` берёт `userId` из тела запроса; `cancel` вообще не проверяет, чья бронь.
- **Сценарий:** пользователь A знает `bookingId` пользователя B и вызывает `POST /api/events/5/bookings/17/cancel`;
  бронь B отменена, место освобождено. Ответ ещё и показывает чужую бронь (`userId`, даты). Так же A может занять
  места «от имени» любого `userId`.
- **Как исправить:** брать пользователя из `sub` токена (`@AuthenticationPrincipal Jwt`), убрать `userId` из тела,
  в `cancel` разрешать только владельцу (и, возможно, организатору события); чужую бронь отдавать как 404.
- **Тест:** USER A отменяет бронь USER B → 404/403, бронь осталась `ACTIVE`; бронь всегда создаётся на `sub`.

### 2. Нет владельца у события
- **Где:** `EventService.update/delete` не проверяют автора; `EventRequest.organizerId` задаёт клиент.
- **Сценарий:** организатор X делает `PUT /api/events/{id}` на событие организатора Y, подменяет `organizerId` или
  удаляет событие вместе со всеми бронями (каскад, решение 003).
- **Как исправить:** `organizerId` = `sub` из токена при создании (убрать из запроса); изменять и удалять только владелец.
- **Тест:** организатор X получает 403 на `PUT`/`DELETE` чужого события; `organizerId` в ответе равен `sub`.

### 3. Самовыдача роли ORGANIZER
- **Где:** `RegisterRequest.role`, `AuthService.register`.
- **Сценарий:** `POST /api/auth/register {"role":"ORGANIZER"}` — и ролевая модель ничего не защищает.
- **Как исправить:** убрать поле из публичной регистрации; организатора назначает администратор (роль `ADMIN`) или
  отдельный процесс подтверждения.
- **Тест:** регистрация с `role=ORGANIZER` создаёт `USER` (или 400); `POST /api/events` после неё даёт 403.

## P2

### 4. `?sort=` и 500 (проверено запуском)
- **Где:** `EventController.list` принимает произвольный `Pageable`.
- **Факт:** `sort=foo` → **500**; `sort=version` и `sort=organizerId,desc` → 200, то есть внутренние поля доступны
  для сортировки (утечка устройства модели и возможность сортировок без индекса, нагружающих БД).
- **Как исправить:** белый список (`title`, `startsAt`) и 400 `ProblemDetail` для остального; либо обработать
  `PropertyReferenceException`.
- **Тест:** `sort=foo` и `sort=version` → 400 с `ProblemDetail`; `sort=startsAt,desc` → 200.

### 5. Конфликт версий события даёт 500 (по коду)
- **Где:** `EventService.update/delete` (`@Transactional`), `ApiExceptionHandler` не знает про
  `OptimisticLockingFailureException`.
- **Сценарий:** организатор правит событие, а в этот момент кто-то бронирует место (версия события меняется) —
  коммит падает, клиент получает 500 «Unexpected server error» и в логе стектрейс, хотя это штатная конкуренция.
- **Как исправить:** обработчик `OptimisticLockingFailureException` → 409 `ProblemDetail` («повторите запрос»).
- **Тест:** два параллельных `update` одного события: один 200, второй 409, не 500.

### 6. Бронь начавшегося события и несуществующего пользователя (проверено запуском)
- **Где:** `BookingService.bookOnce` не сравнивает `startsAt` с `clock.instant()` и не проверяет пользователя.
- **Факт:** событие пятидневной давности и `userId=999999` без записи в `users` — бронь создана.
- **Как исправить:** отклонять бронь, если событие уже началось (409, время из `Clock`); пользователь берётся из токена
  (см. п. 1), плюс внешний ключ (п. 15).
- **Тест:** `Clock.fixed` после старта → 409 и `bookedCount` не изменился.

### 7. Порты БД и Kafka наружу с паролем по умолчанию
- **Где:** `compose.yaml`: `"5432:5432"`, `"9092:9092"`, пароль `postgres`, Kafka без аутентификации.
- **Сценарий:** на ноутбуке в общей сети (кафе, офис) PostgreSQL с `postgres/postgres` доступен соседям.
- **Как исправить:** `127.0.0.1:5432:5432` и `127.0.0.1:9092:9092`; для `app` порты БД и Kafka наружу не нужны вообще;
  пароль БД без значения по умолчанию в `compose.yaml` (как у `JWT_SECRET`).

### 8. Слабый тест идемпотентности
- **Где:** `NotificationKafkaIntegrationTest.redeliveredEvent...`.
- **Проблема:** если убрать `ON CONFLICT DO NOTHING`, второй `INSERT` упадёт на уникальном ограничении, обработчик
  повторит и пропустит запись — в таблице всё равно будет одна строка, тест останется зелёным. Он проверяет БД, а не
  логику идемпотентности. Кроме того, `booking_id` 9001/9002/9003 зашиты в тесте и могут пересечься с настоящими id.
- **Как исправить:** проверять возвращаемое значение/метрику («дубль проигнорирован без ошибки и без повторов») и
  отдельный юнит-тест `BookingEventsListener` с моком репозитория; не зашивать id.

### 9. Неполные сообщения в consumer
- **Где:** `BookingEventsListener.parse` проверяет только `eventId`.
- **Сценарий:** сообщение без `bookingId`/`userId` десериализуется в `0` (примитивы `long`) и порождает мусорное
  уведомление «Booking 0 … user 0».
- **Как исправить:** `Long` вместо `long` в `BookingCreated` и проверка на `null`, или включить
  `FAIL_ON_MISSING_CREATOR_PROPERTIES`; считать такое сообщение нечитаемым (не повторять).

## P3

10. **Юнит-тесты `BookingService`.** `mock(PlatformTransactionManager)` означает, что транзакций нет вообще; проверки
    `verify(saveAndFlush, times(2))` привязаны к реализации. Реальное поведение держат интеграционные тесты, но стоит
    добавить юнит-проверки через результат, а не через число вызовов.
11. **Валидация `EventRequest`.** `organizerId` без `@Positive`; `capacity` без верхней границы (`Integer.MAX_VALUE`);
    `@Future` на `startsAt` в `PUT` мешает исправить опечатку в названии уже начавшегося события.
12. **`Booking.createdAt`** ставится через `Instant.now()`, хотя остальное время идёт через `Clock`: время создания брони
    нельзя зафиксировать в тесте.
13. **«После коммита».** `BookingService` использует `TransactionTemplate`; если `book()` когда-нибудь вызовут внутри
    чужой транзакции, шаблон присоединится к ней и событие уйдёт до коммита. Защита: `TransactionSynchronization`
    (`afterCommit`) или явный запрет вложенного вызова (`PROPAGATION_REQUIRES_NEW`).
14. **Перебор паролей и отзыв токена.** Нет rate limit на `/login` и `/register` (BCrypt нагружает CPU), токен нельзя
    отозвать до `exp`, роль в токене не обновляется до перевыпуска. Подпись HS256 одним общим секретом.
15. **Решение 002** («без FK на users, потому что пользователей нет») устарело: пользователи уже есть. Нужны внешние ключи
    `bookings.user_id` и `events.organizer_id` (миграция V7) и обновление записи 002.
16. **Поставка.** Swagger UI открыт всегда (решение 007); GitHub Actions закреплены тегами `@v4`, а не SHA; базовые
    образы Docker без digest; в CI нет сканирования зависимостей.

## Что проверено и замечаний нет
- **N+1:** сущности связаны только числовыми идентификаторами (`Booking.eventId`), ленивых ассоциаций нет, список
  событий — один запрос плюс `count`. N+1 в текущей модели невозможен; при добавлении `@ManyToOne` проверять заново.
- **Self-invocation транзакций:** нет. `BookingService` намеренно без `@Transactional` (`TransactionTemplate`);
  `EventService.update` вызывает `get` внутри уже открытой транзакции; `@Transactional` на `NotificationRepository`
  вызывается через прокси из слушателя.
- **Секреты в коде и истории git:** только пароль БД по умолчанию `postgres` (документирован) и тестовый
  `JWT_SECRET` в тестовых ресурсах; настоящий секрет нигде не хранится, не попадает в образ и логи.
- **Утечки в ответах:** `UserResponse` без хеша пароля, ошибки без стектрейсов, токены и пароли не логируются
  (тест на вывод). Остаточное: регистрация отвечает 409 на занятый email (осознанный компромисс), список событий
  показывает `organizerId` любому авторизованному.
